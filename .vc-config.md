# vc-x1 config file

Configure the work-repo of a dual repo system. The other repo, we call the agent-repo, is
also a markdown configuration file typically named .vc-config.md.

The code blocks in these config files are in toml format and these blocks are logically
concatenated in the order written here and those become the information used for configuring
the system. The [vc-config.md](vc-config.md) contains the documentation for the
various toml tables used for configuration and it is also used during compilation to define
the valid contents of this file.

The file [vc-config-model.md](vc-config-model.md) is the model: every table and key a workspace
config may carry, each with its default or a typical value. It is generated from the schema, so it
cannot fall behind the keys the binary knows.

The two repos
- work [[1]]
- agent [[2]]
```toml
[repos]
work = "."
agent = ".agent-session"
```

The agent-repo's name on its remote, which clone and sync need when there is no agent-repo yet to
ask
- agent-repo [[9]]
```toml
[remote]
agent-repo = "vc-x1.agent-session"
```

The agent-file family this repo belongs to: its member name and the sibling repos it answers to
- member [[3]]
- template [[4]]
- messages [[5]]
```toml
[family]
member = "vc-x1"
template = "../vc-x1-template/work"
messages = "../vc-x1-messages"
```

The validation commands, each element one invocation, run in order by `vc-x1 validate`
- full [[6]]
- fast [[7]], `cargo test --bins` alone, the schema's example, wink's call 2026-10-20: the full
  list with plain `cargo test` measured the same 8 s as full, since the fourteen `dr1_*` fixture
  tests cost nothing once the fixture is built, so the only fast worth having skips fmt, clippy,
  the integration tests, and the install. Its trial of 2026-09-21 found a rung's failures in what
  it skips, so a rung's review still runs full
- full checks the source and makes no build to run, wink's call 2026-10-21: the dev build is
  `[build] dev` below, which `vc-x1 run --dev` runs first, so what runs is always the current code,
  and the test build full leaves is what the dev build then reuses
```toml
[validate]
full = [
  "cargo fmt",
  "cargo clippy --all-targets -- -D warnings",
  "cargo test -- --include-ignored",
]
fast = ["cargo test --bins"]
```

The build, one list for every profile, run in order with each element one invocation, a plain
`cargo build` naming the chosen profile's `Cargo.toml` profile, so its binary stays in `target/`
and nothing on the PATH is replaced until `vc-x1 install` copies it there, and `--locked` so every
profile's build compiles the same dependencies
- commands [[10]], the build, run by `vc-x1 build` and first by `vc-x1 run` and `vc-x1 install`,
  `{profile.cargo}` filled from the profile `--profile` names, else the default [[19]], release
```toml
[build]
commands = ["cargo build --profile {profile.cargo} --locked"]
```

The install, one list for every profile, written out so the config says what `vc-x1 install` does.
It copies the binary to a `.new` file and then moves it into place, since a copy onto a running
binary fails and a move swaps it in whole, so a copy already running keeps the old code and the
next run gets the new. The list uses `{table.key}` placeholders, filled for the run, so each path
is written once, and `~` is expanded to the home directory, so the value fits every machine.
- dir [[11]], where every profile's binary goes, `~/.cargo/bin`
- commands [[12]], the install, the binary `{profile.bin}` under its file name with the profile's
  `{profile.suffix}` appended, so the dev build sits beside the release and never replaces it
```toml
[install]
dir = "~/.cargo/bin"
commands = [
  "cp {profile.bin} {install.dir}/vc-x1{profile.suffix}.new",
  "mv {install.dir}/vc-x1{profile.suffix}.new {install.dir}/vc-x1{profile.suffix}",
]
```

The profiles `--profile` chooses among, each a `Cargo.toml` profile by its cargo [[13]] property,
its bin [[14]] the binary cargo leaves for it, and its suffix [[15]] what the installed name gets
- release, the default, installed as `vc-x1` at a cycle's Land
- dev, the debug build a rung tries, installed as `vc-x1-dev` beside it, wink's call 2026-10-21:
  after full's `cargo test` it reuses the test build and takes under a second against a release
  build's ten, forty against ten when cold, and its overflow checks and `debug_assert!` suit a
  build that exists to be tested
```toml
[profile.release]
cargo = "release"
bin = "target/release/vc-x1"

[profile.dev]
cargo = "dev"
bin = "target/debug/vc-x1"
suffix = "-dev"
```

The closing commit's default body, `{title}` the cycle title read from the opening, so `vc-x1
commit --closing` needs no `--body` for a closing that says only where its record is
- body [[16]]
```toml
[closing]
body = 'Closes the cycle "{title}". See details in zCLOSED.md.'
```

The cycle's record files, so `vc-x1 commit --closing` moves the In Progress block from the doing
file into the closed file
- doing [[17]]
- closed [[18]]
```toml
[record]
doing = "zDOING.md"
closed = "zCLOSED.md"
```

The acceptance-test fixtures, one dual workspace per name under the directory, inside the
workspace and gitignored, so a fresh clone builds or fetches its own there and the committed config
names no path on one machine
- fixtures [[8]]
```toml
[test]
fixtures = ".fixtures"
```
