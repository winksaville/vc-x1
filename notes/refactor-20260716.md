# Refactor: typed jj facade -> jj-lib in-process (2026-07-16)

The plan-and-design document for the jj refactor program.
Version-control operations are scattered hand-rolled
`run("jj", ...)` spawns (~30 query sites plus every mutation)
with per-module private wrappers, plus raw-git vestiges in
init. Spawning means stderr parsing instead of typed errors,
and jj's single-attempt index-lock acquisition sits outside
our control, so the push `bookmark-set` lock race [[1]] can't
be retried where it fails.

How this file works:

- Each stage below is a `##` section in execution order;
  each is roughly one `X.Y.Z` cycle. Section anchors are the
  durable way to reference a stage from TODO.md, chores, or
  bugs.md.
- This file owns the forward plan and design. When a stage
  ships, its `chores-NN.md` section records the commits and
  narrative as usual; the stage section here gets a one-line
  status link to that chores section, with no duplication.
- The `## In Progress` program block "Refactor: typed jj
  facade -> jj-lib in-process; end subprocess spawning" in
  [TODO.md](../TODO.md) was the short pointer here (promoted
  from `## Todo` 2026-07-24) until the program's retirement
  (2026-08-18), recorded in the as-built ladder below.
- Consolidation (2026-07-24): the remaining stages run as
  **four cycles**, with small stages riding as rungs of a
  neighbor rather than getting their own cycle. Anticipated
  close-out titles (the as-built ladder below carries the
  shipped versions):
  - `refactor: repo registry` (de-gitify init last rung)
  - `refactor: split push.rs + stateless push` (extraction
    first rung)
  - `refactor: jj-lib migration` (may itself split: reads,
    mutations)
  - `refactor: push body-intro validation + trapezoid
    close-out` (validation first rung)

Absorbed former Todos: "Dedup jj subprocess queries behind a

## Stage: facade owns topology

Shipped at 0.75.0
([chores](chores/chores-14.md#refactor-facade-owns-topology)).
Repo resolution becomes facade state, not per-command
preludes.

- `validate-desc` / `fix-desc` por equalization: replace the
  `other_repo_from_config` prelude in both
  (`validate_desc.rs:133`, `fix_desc.rs:152`) with
  scope-aware resolution that no-ops `Side::Bot` when
  absent; body unchanged. The 0.61.0 audit [[2]] called this
  the cheapest equalization and the prototype for the
  topology-from-config rule (topology from `default_scope`,
  not a flag); the remaining implementation gaps live in
  [[2]]'s `## Gap list`.
- Make the bot repo directory name configurable (not
  hardcoded `.claude`; decided 2026-07-15 the name need not
  be `.claude`; decided 2026-07-21 the new default is
  `.bot`). The literal is embedded across
  init/clone/push/sync, `claude_path()`, diagnostic /
  logging strings (`bm-track`'s `.claude(main)=no-jj`),
  ochid path semantics (`/.claude/<chid>`), the
  `~/.claude/projects/<path>` symlink, and docs;
  `.vc-config.toml` already records workspace paths, which
  makes it the natural home. Schema shape decided 2026-07-23: the
  symmetric `work = "/"` / `bot = "/.bot"` pair *replaces*
  `path`/`other-repo` (identical `[workspace]` block on both
  sides, so nothing to cross-check); side detection by
  location, walking up from cwd via `find_workspace_root`
  (root -> work, `<root>/<bot-dir>` -> bot; was the deferred
  half of `0.41.1-6`'s title; design in
  [chores-08 Operations](chores/chores-08.md#operations));
  presence of `bot` is the dual-repo signal (replacing
  presence-of-`other-repo`); POR is `work = "/"` alone.
  - Migration decided 2026-07-23: none. The config records
    each workspace's actual bot dir, so existing workspaces
    keep `.claude` (`bot = "/.claude"`) and their
    `/.claude/<chid>` trailers keep resolving verbatim;
    `.bot` is the *new-init default only*, a
    recommendation rather than a mandate.
  - Still open: the harness-controlled symlink location,
    and the harness's own `<project>/.claude`
    settings/skills dir. Renaming the bot repo splits it
    from the vendor's dir (only bites a workspace that
    *chooses* a non-`.claude` dir).
- `config` command reshape (decided 2026-07-23 during the
  0.75.0-2 review): positional `work|bot|work,bot|<path>`
  target (default `work,bot`), print by default with
  `--validate` switching to check mode; validate covers both
  sides' files plus the identical-`[workspace]`-block
  invariant; `--home` retires; the user-home file stays
  load-bearing but is reachable only via an explicit
  `<path>`.
- Path grammar for `work` / `bot` (pinned 2026-07-23): ochid
  path syntax, where a leading `/` is *the workspace root*
  (workspace-relative, never filesystem-absolute). `work` is
  exactly `"/"`; `bot` is `"/" + one path component`, no
  trailing slash (the bot repo sits directly under the root,
  as side detection and the root walk assume). The `bot`
  value doubles verbatim as the bot-side ochid prefix.
  Defined and *enforced* at 0.75.0-3 (pulled forward from the
  `-4` plan, no downside): every resolver rejects a
  non-`"/"` `work` or a malformed `bot` loudly, since either
  would otherwise be silently ignored or corrupt trailers.
  The `-4` `config --validate` reuses the same check as the
  human-facing report.
- Dual-mode preflight principle (decided 2026-07-23, "my
  opinion ATM"): an operation entering dual-repo mode
  verifies both repos' expected state up front (bot dir
  exists, both configs parse, `[workspace]` blocks identical)
  and on any finding it stops, prints everything known
  (both paths, both blocks), and changes nothing. Mid-flight
  surprises remain per-operation concerns (sync's
  stop-and-inspect, push's rollback); *entry* is gated at
  the one topology resolver the 0.75.0-3 sweep centralizes.
  The full every-invocation form (validate-bot everywhere)
  stays a separate Todo, since it has per-invocation cost
  questions.
- Bisect note: the two repos rewind independently, so checking
  out a pre-0.75.0-2 work commit pairs an old binary + old
  work config with the bot repo's *current* (new-form)
  config, so bot-side lookups fail with "missing
  workspace.path" (loud but cryptic; old binaries are
  immutable, this paragraph is the decoder). Within either
  repo every commit is functional, because schema flips land
  atomically with the configs they read (the 0.75.0-2
  shape), and the per-rung cargo cycle keeps intentionally
  broken commits out of history.

## Stage: repo registry

Shipped as 0.76.0 (2026-07-24 -> 2026-07-28; as-built ladder
and outcome in
[chores-14](chores/chores-14.md#refactor-repo-registry)):
the `[repos]` schema + side detection, the
resolved-agreement preflight (+ self-identification), the
ochid side labels (legacy support consolidated in
`src/legacy_vc_config.rs` for retirement after the repo
migration sweep), the docs sweep, and de-gitify init as the
last rung.
Decided 2026-07-24 (during the 0.75.0-4 review). The
`[workspace]` block becomes a repo registry (stable names
mapped to locations) and the root-anchored path grammar
(leading `/` = workspace root, pinned at 0.75.0-3) is
dropped. Complements the URL-shaped-ochid design in
[forks-multi-user.md](forks-multi-user.md#per-user-bot-repos-via-url-shaped-ochid)
(the "ochid: bot-repo location qualifier" Todo): that entry
owns the published/URL half; this stage owns the local-path
half.

- Rename the section: "workspace" is overloaded (cargo,
  VS Code, and jj itself has `jj workspace`), and vc-x1 is
  medium-agnostic. Settled at pickup (2026-07-24):
  `[repos]`, so config-key paths become `repos.work` /
  `repos.bot`.
- Path semantics for `work` / `bot`: an ordinary path, either
  absolute or relative to the directory containing the
  config file that states it (the standard file-relative
  rule; no leading-`/`-means-root special case). Docs
  recommend relative paths; absolute paths are allowed but
  discouraged, because they commit one machine's layout.
- The literal identical-block invariant cannot survive
  file-relative values (the same bytes mean different dirs
  in each file); it is replaced by **resolved agreement**:
  canonicalize each side's declared pair and require both
  files to name the same two directories. The 0.75.0-3
  coherence preflight keeps its role, comparing reality
  instead of spelling.
- Side detection: the entry that resolves to the config's
  own directory names the side (`work = "."` -> work repo).
  Repos need not be nested.
- ochid trailer prefixes become opaque repo labels resolved
  through the registry, not filesystem spellings: `/` and
  `/.claude` remain valid as historical labels for
  work/bot, so published trailers keep resolving; labels
  are intended to grow into URLs (the forks-multi-user
  design), making trailers clone-portable with no layout
  assumption.
- Committed identity vs local layout: a committed relative
  path is only honest while the repos travel together
  (nested, or siblings under a committed root). Non-nested
  layouts need the registry split (committed name/URL,
  per-machine local path in an uncommitted local file),
  designed here even if URL support lands later.

We think this should run immediately after facade owns
topology (before de-gitify init): the schema is unreleased
and freshly adopted (one external workspace migrated at
0.75.0-2), so moving now means one migration wave instead
of two, and the init/clone rework (de-gitify init, the
template restructure) lands on the final schema instead of
being rewritten twice.

## Stage: stateless push

Shipped at 0.77.0
([chores](chores/chores-15.md#refactor-stateless-push)), with
[split push.rs](#stage-split-pushrs) as its first rung. Scope
grew during the cycle: preflight went too, and the resume point
was replaced by per-stage guards rather than by a derivation,
since nothing needs to decide where to begin if every stage is
safe to repeat.

Retire the push state file and derive resume from repo
reality. Prompted by the 2026-07-20 review of the split-push
extraction ("why does `Stage` live in a file?"): the file's
chief consumers are the two sanity verifiers defending
against it going stale (the 0.37.1 false-success incident is
the canonical failure).

- Standalone `squash-push` is the precedent: stateless, it
  derives everything from the repo.
- Failure-point audit (2026-07-20 session): pre-commit
  failures need no state (nothing mutated); the
  commit-window rollback is same-process; the one real
  cross-process resume (push-work failed, commits exist,
  bookmark ahead of origin, working copies clean) is
  detectable from the repos.
- Converges with the N:1 uncovered-commit detection (Todo
  "vc-x1 push: record uncovered code commits"): both need
  "committed but not yet published".
- **Shipped at 0.77.0-3**, and further than planned: the
  state file, `--restart` / `--from` / `--status`, the
  stale-state verifier, the `[push]` state config keys and
  the `.gitignore` coherence check are gone, and so is
  preflight, whose `sync --check` self-spawn was what forced
  the tests' stage-skipping flag. What replaced the resume
  point is not a derived start but **per-stage guards**:
  each stage no-ops when its work is done, so a rerun is a
  run. The in-process `jj op` rollback stays.
- The "don't grow the state file" rule is retired with the
  file. Moot for the trapezoid stage anyway, now that it is
  a sibling subcommand rather than a push flag.
- Retiring `--from` does not strand the manual
  [trapezoid recipe](../agent-data/jj.md#trapezoid-close-out-recipe):
  its step 4 becomes a bare `vc-x1 push <bookmark>`, because
  the post-reshape repos are exactly the state
  reality-derived resume recognizes. Docs rider on the rung
  that deletes the flag.

## Stage: jj-lib migration

Migrate the facade internals to jj-lib (already a dependency
for read-only commands); removes jj and git spawning
entirely.

- Reads first: `jj log` templates become `Commit` accessors
  (the `src/jj.rs` facade internals; `common::load_repo` /
  `resolve_revset` are the existing in-process machinery).
  Caveat: queries against `@` rely on the spawned CLI's
  working-copy auto-snapshot, since push asks "uncommitted
  changes *right now*?", so the in-process form must
  snapshot first, and a snapshot is an op-store write:
  those reads move with the mutation lift, not before.
- Then mutations: commit, describe, bookmark set/track,
  fetch, push, which is the workspace/transaction/op-store
  lift.
- The index-lock retry loop becomes ours (catch, back off,
  retry) with real error types, the fix vehicle for the
  bugs.md `bookmark-set` lock race [[1]].
- `LocalBareInit`'s `git init --bare` becomes a gix call
  (jj-lib already pulls gix in).

## Stage: trapezoid close-out

`vc-x1 trapezoid-push` builds the trapezoid itself, replacing
the four-step manual procedure. The shape, the base rule, and
the manual steps are specified once in
[the recipe](../agent-data/jj.md#trapezoid-close-out-recipe);
this section covers only what implementing it adds.

Runs at 0.79.0 with
[body-intro validation](#stage-push-body-intro-validation) as
its first rung, after jj-lib so the reshape is in-process. It
was briefly folded into the 0.77.0 stateless-push cycle and
unfolded the same day (2026-07-28); see that cycle's
[chores section](chores/chores-15.md#refactor-stateless-push)
for why the folding argument didn't survive.

### A subcommand, not a flag on push

Decided 2026-07-28, replacing the earlier `push --merge
[<base>]` design:

- **`push` keeps an invariant worth stating: it never
  produces a merge.** A mode flag would rewire the stage
  sequence from inside, which is the classic
  shape-changing-flag smell; a separate verb names the act.
- Three open questions dissolve: mutual exclusion with a
  future `--squash` (separate verbs can't conflict),
  "no state-file growth, re-passed on resume" (nothing to
  re-pass), and clap's optional-value footgun, where `--merge
  [<base>]` needs `--merge=<rev>` to disambiguate from a
  following positional, where a subcommand takes `<bookmark>`
  positionally and `--base <rev>` as an ordinary flag.
- Named for the `<shape>-push` spelling `squash-push` already
  uses. The parallel is the *name*, not the semantics, since
  `squash-push` is a bot-repo operation. Help text opens with
  the bridge for git readers: a non-fast-forward merge, which
  this project calls a trapezoid. "no-ff" is not introduced
  as a third spelling.
- **Duplication is answered by extraction, not by copying.**
  `push` and `trapezoid-push` share nearly everything
  (preflight, both approval gates, message composition,
  commit-work, commit-bot, bookmark-set, push-work, the bot
  squash) and differ by one inserted step. The shared
  pipeline moves into its own module both call; each
  subcommand is a thin front-end over it. The stateless-push
  cycle shrinks that pipeline first, which is what makes the
  extraction cheap.
- **A backend `trait` is the right shape only when a second
  backend exists.** If a git (or other VCS) implementation
  ever appears, converting these concepts to traits with two
  implementations is the natural move and worth doing then.
  Today we are committed to jj, and a trait with one
  implementation buys indirection and no abstraction.

- The merge itself is trivial in-process: a two-parent commit
  in one transaction; no conflicts possible since the base is
  an ancestor of the tip.
- Doing it **in-flight** (see the stage placement below) is
  strictly better than the manual procedure: nothing is
  published in the interim shape, so there is no unreachable
  SHA, no sideways bookmark move, and no backfill embargo
  window. That wart is an artifact of the flag not existing.
- Teach `validate-desc` + the push sanity verifiers the new
  legal shape (two parents, N ochids).
- Assert the parent count **after** the rebase rather than
  trusting jj not to simplify the edge: the manual recipe's
  verification step, promoted to a code check.
- Status: the 0.72.0 attempt to pull this stage forward
  paused on the `support-trapezoid-commits` bookmark and is
  now abandoned as a version; see the
  [parked-branch disposition](#parked-0720-branch-disposition-quarry-not-base)
  (its ladder plan remains the template for this cycle).
  The stage runs here, in program order, on the refactored
  internals, with body-intro validation as its first rung.
  The former enabler Todo "vc-x1 push: pause point between
  commit and publish stages" was retired unimplemented,
  because native merge support supersedes the pause.

Design points settled in the 2026-07-20 session (the parked
cycle's planning):

- Opt-in, never automatic. The trapezoid is a first-party
  shape the user chooses at publish time, which is now the
  choice of *which command to run* rather than a flag. Base
  is the merge's first parent (the parent of the task's
  first commit), `--base <rev>` on the subcommand:
  - branch style (task on a feature bookmark, target
    sitting at the base): base defaults to the target
    bookmark's position
  - main style (task grew on the target, bookmark at the
    work tip): base can't be inferred, so the explicit
    `<base>` revision is required
- The merge step sits after commit-bot, before
  bookmark-set. Chids survive the rebase, so both ochid
  directions are injected normally and stay valid.
- Preconditions: base is a proper ancestor of the work
  tip; close-out has exactly one parent pre-rebase; target
  bookmark at the base or the work tip. Anything else is
  divergence (e.g. a second repo instance moved the
  target), so reconcile first.
- Both styles publish forward. The old bookmark position
  is one of the merge's parents, so the push never forces.
  Post-hoc conversion of an already-published close-out
  stays manual; it needs `--ignore-immutable` only when that
  close-out is already on `trunk()`.
- ochid list: one `ochid:` per work commit the push newly
  publishes; whether to skip commits covered by an interim
  1:1 push is decided at implementation (bot-journal
  trailer scan exists in `squash_push::extract_ochids`).
  The routine case is already **one**, since `0.76.0`'s
  trapezoid carried a single ochid because every rung had been
  pushed 1:1 as it landed.
- Docs ride-along: the two trapezoid variants, which are
  committer-owned (close-out *is* the merge; this
  subcommand) vs PR-style (the integrator authors the merge;
  needs no vc-x1 machinery), and why merge-commit
  integration, never squash/rebase, preserves chids and thus
  ochids (forks-multi-user.md owns the detail).
- `README.md` ride-along: the user-facing section lands on
  the same commit that makes the subcommand real, with
  `vc-x1 trapezoid-push` presented first and the jj
  mechanics and recovery below it or behind links to
  [the recipe](../agent-data/jj.md#trapezoid-close-out-recipe).
  Held until then deliberately: documenting it before it
  exists documents vapor.

## Design risk: op-store coexistence

**Conclusion superseded 2026-07-31 by
[the version coupling policy](jj-version-policy.md).** The
findings below stand and are the evidence that policy rests on;
the verdict at the end does not. Kept as the investigation that
produced it rather than rewritten, so the record shows what was
known when. Two things moved:

- the `jj --version` bullet judged the check as a compatibility
  oracle, which it fails at. As a guard on our own writes it fits
  the risk, and the sample objection it raises survives as a
  limit on what the gate claims rather than as a reason not to
  gate.
- "low-probability, silent, and low-blast-radius" was written
  before we knew prost discards unknown fields, which makes the
  loss symmetric and gives it a named mechanism.

In-process op-store writes must coexist with the user's
external `jj` CLI driving the same repos. Investigated
2026-07-29 (jj-lib 0.41 source, installed jj 0.40.0, jj's
published docs). Findings, and why the obvious mitigation
does not work:

- **Today there is no risk at all.** vc-x1 spawns the user's
  `jj` for every mutation, so it inherits their version. The
  migration *introduces* the coupling; it does not inherit
  one.
- **Structural change fails closed.** `repo.rs:491-569` /
  `workspace.rs:513` raise `StoreLoadError::UnsupportedType`
  when a `type` file names a backend the library lacks, so a
  future `op_store/type` we don't know is a hard error, not a
  guess.
- **The index self-heals.** It carries an explicit format
  version (`COMMIT_INDEX_SEGMENT_FILE_FORMAT_VERSION = 6`,
  checked at `default_index/readonly.rs:303`), and
  `default_index/store.rs:560` responds to a mismatch by
  reindexing, not erroring. Derived data; costs time only.
  Reading those bytes ourselves is inert (it does not
  trigger the rebuild), but the constant is `pub(super)`, so
  a check of our own would duplicate a private constant and
  an internal file layout.
- **The op store has no version stamp.** It serializes with
  protobuf (`simple_op_store.rs:159-218`), whose evolution
  rule is that unknown fields are skipped. So an evolutionary
  change (same backend type, new fields) is *undetectable*
  by construction: a reader cannot distinguish "field absent"
  from "field present and unknown to me". The realistic
  failure is silent information loss, not corruption.
- **jj publishes no compatibility policy.** Checked the core
  tenets, architecture, and concurrency pages: no stability
  guarantee for on-disk formats, and only a bare footnote
  mentioning "automatic upgrades of the repo format" with no
  detail. Everything above is behavior read out of one
  version's source, which they are free to change.
- **Concurrent writers are by design**, which helps the other
  half of the question: "To avoid depending on lock files,
  Jujutsu takes a different approach by accepting that
  concurrent changes can always happen" (concurrency page).
  Operations are content-addressed and op heads are tracked
  by filename.
- **A `jj --version` check does not work.** Users can have
  several jj binaries installed (this workspace has both
  `vc-x1` and `vc-x1-dev`); what our `$PATH` resolves to says
  nothing about what an editor integration, another shell, or
  a later session will run against the same repo. The check
  is a sample, not a gate.

We think the residual risk is therefore low-probability,
silent, and low-blast-radius, but it cannot be enforced
away, so taking it on should be a decision rather than a
step the ladder assumes.

*(That last paragraph is the superseded verdict; see the note at
the top of this section. The decision it asked for was taken on
2026-07-30, and the enforcement it rules out is
[the gate](jj-version-policy.md), which enforces our own writes
rather than compatibility.)*
